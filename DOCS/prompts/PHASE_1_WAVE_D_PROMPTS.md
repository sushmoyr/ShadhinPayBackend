## Cross-cutting decisions

These apply to every Wave D sub-prompt. Override only with an explicit reason
documented in the commit body.

1. **Locked contracts:** the `Vendor` enum (after Wave C) is closed for Wave D
   — all six remaining values (`NAGAD`, `ROCKET`, `UPAY`, `PATHAO`, `MCASH`,
   `STRIPE`) already exist on the enum from Wave A. **No Wave D sub-prompt
   edits `Vendor.java`.** The locked Wave A/B/C contracts (`PaymentProvider`,
   `VendorAuthClient`, `TokenService`, `ErrorCode`, `ApiResult`,
   `AuthenticatedPrincipal`) remain off-limits **except** Track 1's authority
   resolution, which extends `AuthenticatedPrincipal.UserType` consumers without
   changing the enum itself.

2. **Authority namespace:** Spring authorities granted by `JwtAuthorizationFilter`
   are exactly the four strings the existing `@PreAuthorize` annotations expect:
   `MERCHANT`, `ADMIN_VIEWER`, `ADMIN_MANAGER`, `SUPER_ADMIN`. No `ROLE_`
   prefix. Higher admin tiers strictly inherit lower-tier authorities — a
   `SUPER` user's `Authentication` carries all three of `ADMIN_VIEWER`,
   `ADMIN_MANAGER`, `SUPER_ADMIN`. The PRD/TECH_SPEC tables in
   `DOCS/features/identity/PRD.md §4.3` and
   `DOCS/features/identity/TECH_SPEC.md §4.3` are canonical.

3. **JWT library:** `io.jsonwebtoken:jjwt-api` + `:jjwt-impl` + `:jjwt-jackson`,
   version **0.12.6**. Added to root pom `<dependencyManagement>` exactly once
   by Track 1 sub-prompt 1b. No other Wave D sub-prompt adds a root-pom
   dependency.

4. **Token shape and disambiguation:** A merchant API key is the random hex
   string issued by `provisioning.IssueApiKeyUseCase` — opaque, no dots. A JWT
   is a three-segment string matching `^[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+$`.
   `JwtAuthorizationFilter` MUST pass through (no-op, do **not** write 401) any
   `Authorization: Bearer <value>` whose value does not match the JWT regex —
   that's how `ApiKeyAuthFilter` keeps getting a chance to handle merchant API
   keys. The two filters are mutually exclusive per request, never both
   authenticate the same call.

5. **Super-admin seed contract:** `SuperAdminBootstrap` (Spring
   `ApplicationRunner`, ordered after Flyway) is the **only** path that creates
   a SUPER admin on a fresh database. Its six-step behavior is fixed in
   `DOCS/features/identity/TECH_SPEC.md §4.4`. The bootstrap writes directly
   via repositories — it does NOT call `CreateAdminUseCase` (which requires an
   authenticated SUPER caller).

6. **Migration number allocation:** Wave A used V1001–V1011, provisioning
   V1012–V1013, payment-core V1014, Wave C V1016. Wave D uses **V1017** for
   Track 1 (admin tier column) and **no migrations for Track 2** unless a
   vendor needs a new credentials key shape (none expected — the
   `partner-credentials` config is a generic `Map<String, Map<String, String>>`
   that absorbs new vendors via YAML only).

7. **Coverage gate:** Each sub-prompt must keep the per-module JaCoCo gate
   green (no aggregate drop) and ship ≥ 1 test per new artifact. The Wave D
   acceptance gate re-runs the full reactor JaCoCo aggregate (line ≥ 80%,
   branch ≥ 70%).

8. **OpenAPI:** Each Track 1 sub-prompt may add admin endpoints to
   `DOCS/contracts/openapi.json` (regenerated by the acceptance gate, not by
   per-sub-prompt commits). Adapter branches must not touch the spec —
   adapters expose no HTTP surface.

9. **Secret-redaction:** Inherits from Wave C — never log JWT secret, never log
   admin password (plaintext or BCrypt'd), never log the full
   `Authorization: Bearer …` value. Gate verifies via the log-leak grep added
   in Wave C step 6b.

## Wave E readiness (after Wave D)

Wave E is the integration/E2E phase from `DEVELOPMENT_WORKFLOW.md §5`. By the
end of Wave D, every real vendor adapter is in place, the admin surface is
reachable, and the bootstrap super-admin seed runs on every boot. Wave E adds
no new modules — it stitches the existing ones with full Testcontainers +
WireMock scenarios from `DEVELOPMENT_WORKFLOW.md §5.1`.
