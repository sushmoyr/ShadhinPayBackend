# ConfluxPay — Phase 1 Wave A Agent Prompts (index)

> **How to use this file:** This is the index. Each module's prompts live in their own file under `wave-a/`. A fresh Claude Code session reads the relevant module file (and the cross-cutting decisions below) and runs the listed sub-prompts sequentially in the same git worktree on the same feature branch. Modules themselves are fully parallel — five agents in five worktrees can all run at once.
>
> **Why subdivided:** A typical Wave A module is 60–80 source files when you count tests; the 80% JaCoCo gate is unforgiving and the test-fix iteration loop can exhaust a session. Splitting each module into 2–3 sub-prompts keeps each session bounded to ~2–4 hours of agent work, gives clean commit checkpoints, and makes the failure mode "redo the last sub-prompt" rather than "redo the whole module."
>
> **Prerequisite:** Phase 0 is complete and `main` is at commit `d5d77c6` or later. If `mvn -pl conflux-application -am verify` does not pass on `main`, stop.
>
> **Locked Phase 0 contracts (read-only from this point on):** `ApiResult<T>`, `ErrorCode` (14 values), `Money`, the six event records (`MerchantVerifiedEvent`, `UserBlockedEvent`, `PaymentInitiatedEvent`, `PaymentCompletedEvent`, `PaymentFailedEvent`, `PaymentRefundedEvent`), the cross-module use-case interfaces and DTOs in each module's `usecase/` package, `PaymentProvider` and the adapters `port/` types, `ApiKeyAuth` security scheme, `Routes.V1` skeleton.

## Cross-cutting decisions (every Wave A agent reads this)

These are decided up-front so no Wave A agent has to think about them.

### 1. Route constants live per-module, not in `common.constant.Routes`

Each module ships `pay.conflux.backend.{module}.constant.{Module}Routes` (e.g., `IdentityRoutes`, `LedgerRoutes`, `RiskRoutes`, `QuotaRoutes`). This avoids five-way merge conflicts on `Routes.java`. The Phase 0 `Routes.V1.BASE = "/api/v1"` constant is the only thing modules import from `common`.

### 2. `DOCS/contracts/openapi.json` is regenerated by the merge-train orchestrator

Not by individual agents. Agents must not commit changes to that file. The acceptance gate (Prompt 6) regenerates it once after all five branches merge.

### 3. Pre-approved root-pom dependency additions

Only THREE additions are permitted, only by the sub-prompt that needs each, and only in the root `<dependencyManagement>` (with the version pinned) plus the relevant module's `<dependencies>` (no version):

| Sub-prompt | Dependency | Why |
|---|---|---|
| 1c (identity MFA) | `dev.samstevens.totp:totp:1.7.1` | RFC6238 TOTP (battle-tested; faster than hand-rolling) |
| 2b (ledger event listener) | `org.springframework.retry:spring-retry` + `org.springframework:spring-aspects` | `@Retryable` for optimistic-lock retry outside the `@Transactional` boundary |
| 3b (risk SpEL engine) | `com.github.ben-manes.caffeine:caffeine` | In-memory compiled-rule cache |

Any other root-pom edit is forbidden in Wave A; if an agent thinks it needs one, stop and request an explicit cross-cutting decision.

### 4. `NoopTokenService` cleanup

`NoopTokenService` (and its Phase 0 test `NoopTokenServiceTest`) get deleted in Prompt 5a as part of replacing it with `RedisTokenService`. Don't be surprised by the deletion in the diff.

### 5. Wave B's interfaces stay interface-only

`InitiatePaymentUseCase`, `GetBusinessByApiKeyUseCase`, `GetVendorConfigUseCase` are Wave B's responsibility — Wave A leaves them as interfaces with no implementation. `ApplicationModules.verify()` does not require interfaces to have impls; this is fine.

### 6. Coverage gate

80% line / 70% branch per module on the merged branch. Each sub-prompt has its own per-sub-prompt coverage target (50–75% depending on slice) so the early sub-prompts don't fail on coverage that the later sub-prompts will provide. The final sub-prompt of each module always pushes to ≥ 80%.

## Orchestration

### Within a module — sequential

Run the sub-prompts in order in the same git worktree on the same feature branch. Each sub-prompt:
1. Starts on the prior sub-prompt's commit. If the agent doesn't see that commit, it stops.
2. Commits independently (the merge train picks up the whole branch as one merge commit, but within the branch each sub-prompt is its own commit for traceability and rollback).
3. Cumulative coverage targets get progressively higher; the final sub-prompt's coverage push hits 80%.

### Across modules — parallel

The five modules have no inter-dependencies. Launch them concurrently in five worktrees. Recommended pace per module:

| Module | Sub-prompts × hours | Total wall-clock |
|---|---|---|
| `identity` | 3 × 2–3h | 6–9h |
| `ledger` | 3 × 3–4h | 9–12h (Modulith replay test is the time sink) |
| `risk` | 3 × 2–3h | 6–9h (3b is the security-critical session — give it full attention) |
| `quota` | 2 × 2–3h | 4–6h |
| `adapters` | 2 × 2–3h | 4–6h |

If launched fully in parallel, total wall-clock for Wave A is paced by `ledger` ≈ 9–12 hours.

### Merge train

When all five PRs are green, an **orchestrator agent** runs the merge train alphabetical by module: `phase-1/adapters` → `phase-1/identity` → `phase-1/ledger` → `phase-1/quota` → `phase-1/risk`. After each merge:

1. Re-run `mvn -q clean verify` on `main`.
2. Re-run `ModularityTests` and `ArchitectureRulesTest`.
3. If anything regresses (most likely Modulith verify due to a new cross-module access), revert the merge and kick the failing branch back to the originating agent.

After the fifth merge, run the [acceptance gate](wave-a/acceptance-gate.md).

### What to do if a sub-prompt fails its acceptance criteria

Reject the commit. Re-run the sub-prompt with a one-line addendum: `"Your previous attempt failed acceptance criterion X (evidence: ...). Address that specifically before claiming done."` Do not negotiate.

### When Wave A is done

The acceptance gate produces `PHASE_1_WAVE_A_REPORT.md`. If every check is PASS, Wave B begins: `provisioning` first (it depends on identity's `MerchantVerifiedEvent`), then `payment-core` (depends on provisioning, risk, quota, adapters). Wave B is **not** parallel within itself; provisioning must merge before payment-core starts.
