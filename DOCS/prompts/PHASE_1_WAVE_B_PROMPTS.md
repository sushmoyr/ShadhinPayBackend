# ConfluxPay — Phase 1 Wave B Agent Prompts (index)

> **How to use this file:** Same shape as the Wave A index. Each module's prompts live in their own file under `wave-b/`. A fresh Claude Code session reads the relevant module file plus the cross-cutting decisions below and runs the sub-prompts sequentially in the same git worktree on the same feature branch. **Unlike Wave A, the two Wave B modules are sequential, not parallel:** `provisioning` must merge to `main` before `payment-core` starts.
> 
> **Why sequential:** `payment-core` directly injects `provisioning`'s `GetBusinessByApiKeyUseCase` and `GetVendorConfigUseCase` impls. Running both modules in parallel would force `payment-core` to mock interfaces that are about to land for real — wasted work and merge-conflict risk on the application config that wires them up.
> 
> **Why subdivided:** Same reason as Wave A — keeping each session ≤ 2–4 hours of agent work, with clean per-sub-prompt commits and a coverage ramp that lets early sub-prompts ship without failing the 80% gate.
> 
> **Prerequisite:** Wave A is complete and `main` is at commit `286cce1` or later. If `mvn -pl conflux-application -am verify` does not pass on `main`, stop. The Wave A locked contracts in `PHASE_1_WAVE_A_REPORT.md` § "Locked Wave A Contracts" are read-only — Wave B agents that need to touch them stop and ask.

## Cross-cutting decisions (every Wave B agent reads this)

These are decided up-front so no Wave B agent has to think about them.

### 1. Wave A contracts are read-only

The "Locked Wave A Contracts" section of `PHASE_1_WAVE_A_REPORT.md` is binding. Specifically:

- Route constants per-module (`IdentityRoutes`, `LedgerRoutes`, `QuotaRoutes`, `RiskRoutes`) — Wave B ships **`ProvisioningRoutes`** and **`PaymentCoreRoutes`** (its public API surface), no edits to existing ones.
- Cross-module use-case **interfaces** in `provisioning/usecase/` and `payment-core/usecase/` (`GetBusinessByApiKeyUseCase`, `GetVendorConfigUseCase`, `BusinessContext`, `VendorConfigDescriptor`, `InitiatePaymentUseCase`, `InitiatePaymentRequest`, `PaymentInitiationResult`) — Wave B implements them but does **not** change the method signatures or DTO shapes already on `main`. The interface signatures are byte-locked.
- The six event records (`MerchantVerifiedEvent`, `UserBlockedEvent`, `PaymentInitiatedEvent`, `PaymentCompletedEvent`, `PaymentFailedEvent`, `PaymentRefundedEvent`) — field shapes are frozen.
- The `ApiResult<T>` envelope, `ErrorCode` enum (14 values), `Money` record, `ApiKeyAuth` security scheme — unchanged.

If a Wave B agent thinks an interface needs a new parameter, **stop and request a cross-cutting decision** rather than silently breaking the contract.

### 2. `DOCS/contracts/openapi.json` is regenerated by the merge-train orchestrator

Not by individual agents. The Wave B acceptance gate (Prompt 9) regenerates it once after both branches merge. Agents must not commit changes to that file.

### 3. Pre-approved root-pom dependency additions

Only THREE additions are permitted, only by the sub-prompt that needs each:

| Sub-prompt                                      | Dependency                                                                                                                                                                    | Why                                                                                                                 |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 7a (provisioning schema)                        | none                                                                                                                                                                          | AES-GCM uses `common`'s existing `EncryptionService` (Phase 0). API-key SHA-256 uses `java.security.MessageDigest`. |
| 8a (payment-core schema)                        | `com.fasterxml.jackson.module:jackson-module-parameter-names` only if not already transitively present (verify first; Spring Boot 3.4 starter typically already includes it). | Required for clean (de)serialization of `IdempotencyRecord.responsePayload` (JSONB ↔ record).                       |
| 8b (payment-core callback + webhook dispatcher) | `org.springframework.retry:spring-retry` — **already added in Wave A 2b**. No new add needed; reuse.                                                                          | `@Retryable` for the webhook outbox dispatcher.                                                                     |

Any other root-pom edit is forbidden in Wave B; if an agent thinks it needs one, stop and request an explicit cross-cutting decision.

### 4. Flyway migration numbering

Wave A claimed `V1001` (identity) through `V1011` (identity MFA). Wave B agents use:

| Sub-prompt                 | Migration files                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 7a (provisioning schema)   | `V1012__provisioning_schema.sql` (businesses, vendor_configs, api_keys), `V1013__provisioning_seed_partner_vendors.sql`                                       |
| 8a (payment-core schema)   | `V1014__payment_core_schema.sql` (transactions, webhook_outbox, idempotency_records)                                                                          |
| 8b (payment-core callback) | `V1015__payment_core_pending_recovery_index.sql` (partial index on `transactions(status) WHERE status = 'PENDING_RECOVERY'` for the reconciliation scheduler) |

If an agent needs more, they get the next available `V1016+` slot in the same sub-prompt and document it in the commit message.

### 5. Idempotency key scope

`X-Idempotency-Key` is scoped to `(businessId, key)`, **not** `(merchantId, key)`. Rationale: one merchant may own many businesses (per provisioning PRD §3.1 and §5.2 isolation guarantees) — scoping by business prevents cross-business idempotency collisions while still preventing double-charges within a business.

The `payment-core` `TECH_SPEC.md` §5.1 says `idempotency:{merchantId}:{requestKey}` — Wave B uses `idempotency:{businessId}:{requestKey}` instead. Document the deviation in the 8a commit message.

### 6. PARTNER vs CUSTOM dispatch

- **PARTNER mode** uses platform credentials (`conflux.adapters.partner-credentials.{vendor}.*` — Wave B may add this config block; values are env-var-driven in real envs, blank in tests). Quota is metered.
- **CUSTOM mode** uses the merchant's encrypted `VendorConfig.credentials` (resolved by `GetVendorConfigUseCase`'s impl). Quota is **skipped entirely** (no reservation, no usage row).

The mode flows from `provisioning` — `payment-core` never defaults it locally.

### 7. Coverage gate

80% line / 70% branch per module on the merged branch. Per-sub-prompt targets ramp from 55–60% on the first sub-prompt to ≥ 80% on the final.

## Orchestration

### Within a module — sequential

Run the sub-prompts in order in the same git worktree on the same feature branch. Each sub-prompt:

1. Starts on the prior sub-prompt's commit. If the agent doesn't see that commit, it stops.
2. Commits independently for traceability and rollback.
3. Cumulative coverage targets get progressively higher; the final sub-prompt's coverage push hits 80%.

### Across modules — sequential (not parallel)

| Order | Module                                  | Wall-clock (est.)          |
| ----- | --------------------------------------- | -------------------------- |
| 1     | `provisioning` (7a → 7b → 7c)           | ~ 6–8 hours of agent work  |
| 2     | (merge `phase-1/provisioning` → `main`) | merge-train run            |
| 3     | `payment-core` (8a → 8b → 8c)           | ~ 8–10 hours of agent work |
| 4     | (merge `phase-1/payment-core` → `main`) | merge-train run            |
| 5     | Acceptance gate (9)                     | ~ 1 hour                   |

Total wall-clock for Wave B: ~ 16–20 hours of agent work + 2 merge-train runs + 1 acceptance gate.

### Merge train

After each module's branch is fully green, the orchestrator runs the merge train:

1. Rebase the feature branch onto current `main`.
2. Run `mvn -q clean verify` on the rebased branch.
3. Merge with `--no-ff` to preserve the feature commit boundary.
4. Push.

`provisioning` must merge cleanly before `payment-core` starts — the `payment-core` agent needs the `provisioning` impls visible on `main` to autowire them.

## Wave C readiness (after Wave B)

Wave C is the **real-vendor adapters** wave (Bkash, Nagad, Stripe, …). Wave C agents implement the `VendorAuthClient` interface and the `PaymentProvider` port per vendor, plug into the `ResilienceConfig` circuit-breaker registry, and use the `VendorWireMockExtension` harness for contract tests. Wave C is fully parallel (one agent per vendor) and has no dependencies on Wave B's controllers — only on the locked port types Wave A already shipped.

**Wave B unblocks Wave C only insofar as `payment-core` is the consumer of the adapter port.** Without Wave B, a real Bkash adapter has no orchestrator to call it.
